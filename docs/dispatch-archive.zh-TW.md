# 派遣紀錄（dispatch archive）

每一次子 Agent 派遣都會寫進 `state_dir/dispatch/`（`dispatchlog.go`）：每行一筆 JSON 紀錄，每個本地日期一個檔案
（`YYYY-MM-DD.jsonl`），操作者的回饋另外寫在 `feedback-YYYY-MM-DD.jsonl`。建議按鈕、自動事件調查的每日次數、
`shentu dispatch stats` 和每日報告都會讀這些紀錄。這份文件寫給要改紀錄內容的人。

## 紀錄裡可以放什麼

- 只放數量和列舉值，不放自由文字：角色、狀態、原因、閘門代碼、沒查到的原因都是固定字詞；發現只按嚴重度計數；
  觸發來源存雜湊；位址存標準寫法。子 Agent 或模型寫的文字一律不存。
- 讀回時每個欄位都會檢查（`dispatchRecord.check`、`feedbackLine.ok`）。檢查不過的行算成讀不到。派遣紀錄檔
  （`YYYY-MM-DD.jsonl`）有讀不到的行時，自動事件調查會停止，直到執行 `sudo shentu dispatch repair` 把它移到
  `*.jsonl.bad`；回饋檔（`feedback-YYYY-MM-DD.jsonl`）有讀不到的行時，只會跳過並計數，不會停止任何東西。

## 新增欄位

從 v0.5.4 起，讀取的版本遇到不認得的欄位，會照樣讀這一行：不認得的欄位忽略，認得的欄位照舊檢查，這種行另外計數
（`dispatch stats`，JSON 是 `unknown_field_lines`，每日報告也會列出）。`repair` 不會移動這種行。v0.5.4 以前的版本則會
整行拒讀（見 CHANGELOG v0.5.4 的升級須知）。

所以新欄位必須是舊版看不到也沒關係的欄位：

- **限制性的狀態不能只靠新增欄位表達。** 例如建議已失效、已用掉、已撤銷，或某次派遣不能再據以行動：舊版會忽略不認得的
  欄位，降版之後看不到這個限制，就會放行原本禁止的事。限制要用舊版認得、而且舊版 `check()` 會拒絕的欄位值來表達
  （舊版因此讀不到這一行，等於 fail closed），或者存在舊版本來就會讀的另一個檔案。用已知欄位值表達限制的做法
  只能用在派遣紀錄：舊版讀不到回饋行時只會跳過、照常進行，限制如果寫在回饋檔裡就會不見（fail open）。
- 新欄位和其他欄位一樣，只放數量和列舉值，並由新版的 `check()` 檢查。
- 舊版的任何輸出都不會顯示不認得欄位的內容；之後也要維持這一點（不要寫「把所有欄位都印出來」的程式）。
- 只有舊版必須整行拒讀的改動，才調高 `dispatchVersion`。
