The night watch.

While you sleep, Shentu patrols your server and watches for requests aimed at its real weak spots. If something is wrong, you get one message in plain words.

It starts in the courtyard.

Logins and open ports first: each one lights up as the lantern passes.

03:04

One lantern, one check.

Processes, then packages with known exploits; what the light reaches is checked off.

03:09

In the back hall it reads the code.

Every site on the machine, line by line, with its own rules. The code never leaves the server.

It finds the one thing wrong.

A new file in the uploads folder runs whatever a stranger posts to it.

  9. v0.3.0 11-13

    70 rules

    19 changes

    • Windows Server 2022 and 2025, verified on GitHub-hosted windows-2022/2025 runners (amd64; arm64 built too): a Windows collector reads the host through the Windows APIs only (registry, services, processes, sockets, accounts, scheduled tasks, the event log, WMI and the firewall), no PowerShell and no external commands.
    • Windows checks: autostart entries (Run keys, services, scheduled tasks, startup folders, WMI event subscriptions), RDP without NLA, SMB signing and SMBv1, insecure WinRM, firewall profiles, Defender state and exclusions, logon failures and cleared logs.
    • Missing Windows updates against Microsoft's monthly security releases (MSRC), with the CISA KEV list marking the exploited ones first.
  10. v0.3.1 11-16

    127 rules16/97 caught

    New rules enshrined

    • Code audit rules: 70 → 127 (PHP 25 → 51, Python 22 → 43, JavaScript and TypeScript 23 → 33). PHP: WordPress, Laravel, Symfony, Joomla, Drupal, CodeIgniter, Yii and Smarty sinks, sockets and HTTP clients, XML DTDs, template strings, crypto keys and shortcodes (#76). Python: keyword arguments (args=, search_filter=, where=), ldap3 filters and helper flows (#36). JavaScript and TypeScript: Koa and chained Express responses, BSON and launder sanitizers, Host-header redirects and SSRF; .execute( counts only on a receiver that may be a database client (#70).
    • The v0.2.5 known false positives are fixed in the engine: TypeORM repository calls in a file importing typeorm are no MongoDB queries, unless the file uses a MongoDB repository, driver or Mongoose (unless_imports, #59); spawn() and execFile() with shell: true are reported only when the command or its arguments carry input, not the options (several [[args]] blocks per sink, #62); a Server-Sent Events handler (Content-Type: text/event-stream set on every path) is no XSS (unless_content_type, #58; unless_at, #57); ->get_settings() is Elementor widget input only in classes extending \Elementor\Widget_Base (#60); a placeholder list built by array_map with a callback returning a constant is no input (#61); zipfile.ZipFile(request.files[...]) opens the upload's stream, not a path (unless_subscript, #67).
    • js-ssrf-http-request now reads the referrer and origin in Koa, hapi and Fetch API spelling (ctx.request.header.referer, request.headers.referer, request.headers.get('x-callback-url'); not Host), which were missed. Input written into a prepared statement's text is reported once, by php-sqli-prepare-query-text, instead of also by php-sqli-string-concat. The benchmark numbers are unchanged.
  11. v0.4.0 11-18

    127 rules

    21 changes

    • Attack detection (Linux): each patrol round reads the web server's logs and picks out the requests aimed at vulnerabilities this host really has. It alerts; it never blocks on its own. What it cannot see and what it may miss are listed in docs/attack-detection-limits.md.
    • The vulnerability surface: the daily round saves what this host is known to be vulnerable to in state_dir/surface.json, and the other rounds read it: code audit findings, with the routes registering the handler a finding sits in when the same file shows them (#84); advisories of application dependencies and of installed OS packages, compared in dpkg's and rpm's version order; installed WordPress plugins and their versions (#91). A surface missing, unreadable or older than 26 hours is said in the round's notices and the report, never used quietly.
    • Log sources: the access logs nginx and Apache are configured to write, custom formats included, PHP-FPM's logs and journald for application units, read from where the last round stopped across rotation (#85). A log counts as verified only when root alone could have written it; otherwise its attempts are marked unverified and the alert names the reason.
  12. v0.4.1 11-20

    127 rules

    12 changes

    • The host survey warns about nginx 1.9.5 through 1.31.8 serving HTTP/2 (a listen ... http2, or http2 on for a server): CVE-2026-123007 and CVE-2026-123633, HTTP/2 memory corruption that lets a client crash the workers. Upgrade to 1.31.9 or 1.30.7, or to the distribution's fixed package; until then, turning HTTP/2 off avoids it. It is advice: the configuration is not changed. A distribution package whose changelog names the CVEs (a backported fix) is not warned about; the package scan reports the distributions' advisories once they reach OSV, and this check covers nginx.org's packages and builds from source, which that scan does not.
    • A web log owned by the server's own account (nginx on Rocky Linux, say) can back a block, as a log root owns can, when nothing else runs as that account: no PHP-FPM pool, systemd unit, crontab, supervisord program, sudo or doas rule or login shell, and at the patrol no process but the server's own; the account databases come only from the files, and everything checked was read. Anything unread leaves the log web_user_writable. The shared default accounts (www-data, apache, nobody) never count. The other conditions are in the limits document, docs/attack-detection-limits.md, under "Which web logs can back a block".
    • nginx's access log sent to journald (access_log syslog:server=unix:/dev/log,...) is read and verified line by line: a line counts only when it came over syslog from nginx's own program, running as nginx's worker account in nginx.service. A line another program sent is read but not verified.
  13. v0.4.2 11-20

    127 rules

    13 changes

    • The JavaScript rules follow a route handler's request whatever it is called: a parameter not named req ((r, s) =>), a Koa context not named ctx, an alias (const q = r, const h = r.headers) and destructuring (({ headers }, res) =>, const { headers, hostname: hn } = r, const { host } = req.headers). So r.hostname, r.get('host'), c.host and a destructured headers are reported now; a Host header read this way goes to js-ssrf-host-header, other headers to js-ssrf-http-request. A request header index is read in lower case, as Node stores it (r.headers['Host']). In the SSRF rules, Koa's ctx.header and ctx.request.get( are sources too, and so are ctx.request.header.host and ctx.request.headers.host for the Host header (#106).
    • NestJS: @Request() counts as the handler's request, as @Req() does, in the 13 JavaScript rules that read @Req() (SSRF, SQL and NoSQL injection, command injection, code evaluation, path traversal, LDAP injection, deserialization). Both count as NestJS's only when the file, or another file of the project, imports @nestjs/common or @nestjs/core; elsewhere they are an object like any other (#103, #106).
    • Python: global and nonlocal continued with a backslash are read to the end of the statement, so a name on the next line is declared too (#103).
  14. v0.4.3 11-20

    127 rules

    10 changes

    • SSRF: after a URL's host is checked, console.log(u), JSON.stringify(u) or String(u) no longer ends the check, while the file uses console, JSON and String only to call them (no parameter or declaration of those names, no console.log = f) and holds nothing that may replace them unseen (a global object such as globalThis other than read through a named member, eval, Function(, a with statement, anything under a built-in's prototype) (#119).
    • JavaScript route handlers: destructuring with a string key, const { 'x-forwarded-host': xfh } = req.headers, is followed, so the value is reported by js-ssrf-host-header instead of js-ssrf-http-request. In a Koa route handler, a destructured parameter taking request (({ request }) => request.header.host) is read as Koa's context when the file, or another file of the project, imports koa, @koa/router or koa-router (#119).
    • New sources: Next 15's (await headers()).get(...), so a Host header read that way and passed to a redirect is reported by js-open-redirect-next; Laravel's Request::query( and Request::get( in php-sqli-orderby-identifier (DB::raw, ->orderBy() (#118).
  15. v0.5.0 11-20

    127 rules

    3 changes

    • Sub-agents (Linux, one host): in the Telegram bot and shentu chat, the agent can hand read-only checks to up to 3 sub-agents with the dispatch tool, each in one role: patrol, surface, attack or incident (#101). Each role has a fixed list of read-only tools; a sub-agent cannot block or unblock an address, notify, use a skill or dispatch again. They run one after another. Patrol rounds and the eval bot never dispatch.
    • Limits: a sub-agent gets at most 6 model calls, 3 tool calls a step, 2048 output tokens a call, 40,000 tokens and 5 minutes; a dispatch at most 120,000 tokens and 12 minutes, and the monthly budget still applies. Tokens are estimated before each call and counted after it, reasoning tokens included. A sub-agent stopped by a limit, or one that does not answer in the required report, is reported incomplete with the reason, never as done. A model call cut off by a time limit is no longer retried.
    • Reports: each sub-agent answers in a fixed JSON shape (findings, proposals, what it did not check), checked field by field and masked, and the agent reads it marked untrusted. A proposal to block is only a suggestion: after a dispatch, every block_ip or unblock_ip in that conversation asks for the ✅ button even with [bot] confirm = 4, until /new, and its audit log line names the dispatch. The bot's progress message shows the sub-agents' steps (the last 12), and a tool name it does not know as "unknown tool".
  16. v0.5.1 11-20

    127 rules

    7 changes

    • Dispatch archive (#112): each sub-agent dispatch is saved to state_dir/dispatch/<date>.jsonl (0600 in a 0700 directory, kept 30 days) before its reports go back: roles, statuses and reasons as fixed words, counts, and the proposed addresses in canonical form with what the Telegram gate says of each. No text a sub-agent or a log wrote is kept. Every field is checked when a record is written and when it is read; an archive another user could write, or a link, is not read. The daily report has a section on the last day's dispatches, with addresses masked to /24 (/64 for IPv6).
    • Proposal buttons (#116, #122): after a Telegram answer that dispatched, the bot lists the proposed blocks, with a button for each one that passes the checks block_ip runs from Telegram (#108's gate included) at that moment and was written in canonical form, at most five; any other gets a fixed word for why. A button carries only the dispatch id and a number. Pressing it runs the checks again, then asks for ✅ (with [bot] confirm = 4 too), then blocks. A press is refused for another pairing, after 24 hours, a second time (after a restart too), or when the archive's address differs.
    • Automatic incident checks (#117), off by default ([agents] auto_incident): an L3 group the patrol pushed dispatches the read-only incident sub-agent on its own. One a round, at most 3 a day, a group once a day; none for unverified or overflow groups, none without [budget] monthly_tokens or past 80% of it, and none while the archive or log.jsonl cannot be read to its end. The notice carries fixed words and numbers; its proposals get the same buttons, sent only while the bot service runs and can change the firewall.
  17. v0.5.2 11-20

    127 rules

    9 changes

    • The sub-agents' own model (#135): [agents] base_url, model and api_key_env give them a model of their own; unset, they use [llm]. A model outside this host (anything but 127.0.0.0/8, ::1 and localhost) needs [budget] monthly_tokens, or no sub-agent runs and nothing is sent; a dispatch that used one says so to the agent, in the archive and in the daily report. What it is sent is masked as before. From it, an error answer keeps only its status, as its text could quote the key; redirects are not followed, and a request that fails keeps only the kind of failure, not its URL. [llm]'s errors have the key replaced, as is and in its common encodings, before they are cut.
    • Sub-agents at once (#136): on a model outside this host they run together, each with an equal share of the dispatch's token cap, when this month's token limit has room for a whole dispatch and, with monthly_cost set, under half of it is spent. On a model at this host, in any address form, they still take turns.
    • sudo shentu dispatch repair (#134): moves the archive's unreadable lines to <date>.jsonl.bad and drops empty ones, so automatic incident checks resume without waiting up to 72 hours. Files are replaced in one rename, and the archive's lock is dispatch/.lock. On Windows it and dispatch stats run from an elevated prompt; run by anyone else, both say so before reading the configuration.
  18. v0.5.3 11-22

    127 rules

    14 changes

    • A proposal button pressed always gets an answer (#163): it says at once that it checks the address again, the log notes the press (proposal_press) before the checks, the checks run within a minute and past it the press is refused with the gate's word, and a failure inside is answered and logged. As before, a pressed button is used up whatever follows: one refused because its checks ran out of time, failed or were cut by a restart cannot be pressed again, and the next check's buttons are the ones to use.
    • Telegram blocks ask only what the gate would allow (#155, #158): from a chat channel, block_ip runs the checks of #108's gate before asking for ✅. An address the gate refuses is refused at once, with no ✅ to press; the agent is told the gate's fixed word (and the address), and the gate's own message stays in the server's log only. When the block itself fails after the confirmation, its error too stays in the log only. Confirmed blocks are checked again when they run, as before.
    • While the bot waits (#156, #158): a message sent meanwhile is told what it waits for (the ✅ above, the authenticator code, or the server's approval with sudo shentu bot approve) instead of "Still working"; a question sent meanwhile is not passed to the agent (the authenticator code and the commands /lockdown, /new, /usage and /attacks still work). A proposal or suggestion button pressed meanwhile stays, to be pressed again later; a suggestion is no longer used up.
  19. v0.5.4 Coming soon

    127 rules

    In progress

    • Shared AI budget (#161): a dispatch from the bot, shentu chat or the automatic incident check reserves its whole token cap in state_dir/reservations.json while it runs, and every budget check counts the others' reservations, so together they overspend [budget] monthly_tokens by about one dispatch's cap (120k tokens) plus the answer in progress. Upgrading: while a dispatch runs, a question elsewhere can be told that its reservation leaves too little of the month's budget (it is released within about 17 minutes); a reservations file that cannot be trusted stops every AI answer and dispatch until it is moved aside (the bot says which file); and auto_incident with monthly_tokens of 150000 or less now warns, as no automatic check could ever start.
    • Model prices (#162): [agents] price_per_mtok_in and price_per_mtok_out (dollars per million tokens) price each dispatch's reservation at its token cap times the higher of the two, so the monthly cost limit is shared between dispatches as the token limit is. When only the cost limit is filled by the others' reservations, the reply names the dollars reserved.
    • shentu usage and the bot's /usage count the sub-agents' model calls (and any other actor's) (#164): they were left out of the totals, and a dispatch's calls now have a line of their own.
