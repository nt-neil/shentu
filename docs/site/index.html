The night watch.

While you sleep, Shentu patrols your server and watches for requests aimed at its real weak spots. If something is wrong, you get one message in plain words.

InstallSource on GitHub

Scroll to walk the night watch

03:00

It starts in the courtyard.

Logins and open ports first: each one lights up as the lantern passes.

03:04

One lantern, one check.

Processes, then packages with known exploits; what the light reaches is checked off.

03:09

In the back hall it reads the code.

Every site on the machine, line by line, with its own rules. The code never leaves the server.

03:12

It finds the one thing wrong.

A new file in the uploads folder runs whatever a stranger posts to it.

03:15

Someone is knocking on that door.

A request hit a hole the shop's code really has, and the reply came back far larger than usual.

  12. v0.4.1 11-20

    127 rules

    12 changes

    • The host survey warns about nginx 1.9.5 through 1.31.8 serving HTTP/2 (a listen ... http2, or http2 on for a server): CVE-2026-123007 and CVE-2026-123633, HTTP/2 memory corruption that lets a client crash the workers. Upgrade to 1.31.9 or 1.30.7, or to the distribution's fixed package; until then, turning HTTP/2 off avoids it. It is advice: the configuration is not changed. A distribution package whose changelog names the CVEs (a backported fix) is not warned about; the package scan reports the distributions' advisories once they reach OSV, and this check covers nginx.org's packages and builds from source, which that scan does not.
    • A web log owned by the server's own account (nginx on Rocky Linux, say) can back a block, as a log root owns can, when nothing else runs as that account: no PHP-FPM pool, systemd unit, crontab, supervisord program, sudo or doas rule or login shell, and at the patrol no process but the server's own; the account databases come only from the files, and everything checked was read. Anything unread leaves the log web_user_writable. The shared default accounts (www-data, apache, nobody) never count. The other conditions are in the limits document, docs/attack-detection-limits.md, under "Which web logs can back a block".
    • nginx's access log sent to journald (access_log syslog:server=unix:/dev/log,...) is read and verified line by line: a line counts only when it came over syslog from nginx's own program, running as nginx's worker account in nginx.service. A line another program sent is read but not verified.

    127 rules

    13 changes

    • The JavaScript rules follow a route handler's request whatever it is called: a parameter not named req ((r, s) =>), a Koa context not named ctx, an alias (const q = r, const h = r.headers) and destructuring (({ headers }, res) =>, const { headers, hostname: hn } = r, const { host } = req.headers). So r.hostname, r.get('host'), c.host and a destructured headers are reported now; a Host header read this way goes to js-ssrf-host-header, other headers to js-ssrf-http-request. A request header index is read in lower case, as Node stores it (r.headers['Host']). In the SSRF rules, Koa's ctx.header and ctx.request.get( are sources too, and so are ctx.request.header.host and ctx.request.headers.host for the Host header (#106).
    • NestJS: @Request() counts as the handler's request, as @Req() does, in the 13 JavaScript rules that read @Req() (SSRF, SQL and NoSQL injection, command injection, code evaluation, path traversal, LDAP injection, deserialization). Both count as NestJS's only when the file, or another file of the project, imports @nestjs/common or @nestjs/core; elsewhere they are an object like any other (#103, #106).
    • Python: global and nonlocal continued with a backslash are read to the end of the statement, so a name on the next line is declared too (#103).

A proposal to block is only a suggestion: after a dispatch, every block_ip or unblock_ip in that conversation asks for the ✅ button even with [bot] confirm = 4, until /new, and its audit log line names the dispatch.   21. v0.5.6 11-24

    127 rules

    15 changes

    • A file cut short says what cut it (#172). The code audit's unfinished files carry a cause: the token cap, the file's time limit, nesting, a rule's work cap for following calls, the project's cap (its time, memory or tokens), a call that may reach another file with no one callee to follow, or a callee's summary cut short (with why: its own work cap, a chain of summaries too long, too many parameters, or a cut inside it). The CVE bench counts files whose calls were not all followed, which it did not count before, and lists cuts by cause.
    • PHP function and method names in sinks and sanitizers match in any case, as PHP calls them (#189). System($_GET['x']), SYSTEM(...), \SYSTEM(...), System(...) inside a namespace and Shell_Exec($c) in a function a call reaches now report as the lower-case spelling does, and a sanitizer written EscapeShellArg($x) cleans. A method that happens to be named system ($o->System(...), Task::SYSTEM(...)) is still no sink. JavaScript and Python names keep their case. A builtin named in a string with an escaped backslash (array_map('\\system', $x), "\\system"), which PHP reads as \system, is that builtin as well. A pattern naming a PHP function no longer matches a class built with new (new File($p), new System(...)) or a function of a namespace (Storage\file($p), and namespace\file($p) in a file that declares a namespace), as the lower-case new file( and A\file( did before; \file($p) is still PHP's. The method and class names of member patterns match in any case too (#198): $wpdb->Query(...) and $wpdb->GET_RESULTS(...) are php-sqli-wpdb-unprepared's sinks, $wpdb->Prepare(...) cleans, and DB::RAW(...) is a sink; a variable keeps its case ($WPDB is not $wpdb).
    • Calls through callables are followed (#182, #184, #188). A PHP function that calls its own parameter ($cb($v), as tap() and Arr::first() do) is followed at each caller with what the caller passes: a closure, a function name ('run_cmd', 'Cmd::run'), an array callable ([Cmd::class, 'run'], [$this, 'run']) or a first-class callable (run_cmd(...)). A closure handed to a PHP builtin that calls it (array_map, array_filter, array_walk, usort, array_reduce, preg_replace_callback, call_user_func and others) is analysed with the input the builtin gives it, and a builtin's name given as the callable is that builtin: array_map('system', $_GET['x']) and array_map(function ($v) { system($v); }, $_GET['a']) now report. Fewer files are left with calls not followed (#174, #178, #179, #182): Python's standard-library imports (import json in a package with its own json.py) and a closure that cannot leave its function are no longer taken as calls of the project's other files. On the E7 corpus, laravel-framework's unfinished files went from 280 to 115 and Django's from 135 to 24.
  22. v0.5.7 11-26

    127 rules

    20 changes

    • PHP rules read filter_input(). A value from filter_input(INPUT_GET, ...), INPUT_POST or INPUT_COOKIE, and from an application's own method of that name (->filterInput(, ->filter_input() when its first argument is one of these constants, is request input in each PHP rule that reads $_GET, $_POST or $_COOKIE. A first argument that is a variable or another constant (such as INPUT_SERVER) is not. A number or bool filter (FILTER_VALIDATE_INT, FILTER_VALIDATE_BOOL, FILTER_SANITIZE_NUMBER_INT and others, also as a named filter: argument) gives a value with no input in it, but not with flags or-ed into it (FILTER_VALIDATE_INT | FILTER_NULL_ON_FAILURE is another filter ID, which PHP 7 reads as FILTER_DEFAULT); FILTER_SANITIZE_SPECIAL_CHARS cleans in the rules that take htmlspecialchars() as a sanitizer; a URL filter does not clean.
    • macOS: a listening socket netstat gives with pid 0 has no owner to name, so the list of listening ports is marked partial and says how many, no longer complete as if every owner were known.
    • PHP rules know an application's own guard function. A function that returns true only after a check of its path parameter (an allowlist, as Welcart's usces_is_reserved_file(), or realpath($p) with strpos($real, $base) === 0) cleans the value it was given where its result is true (if (guard($f)) { ... }, or after if (!guard($f)) { die(); }), also as a method of another class. A guard that assigns its parameter, returns true before the check, or only checks that the file exists does not. strpos( and stripos( compared === 0 or !== 0 are a prefix check in the path rules, of their first argument only (strpos('/var/logs/', $real) holds for / and /var). Where realpath($p) found the file, $p is no longer a URL or a phar:// wrapper for the server-side request and phar rules; the path rules still report it. An in_array() lookup of basename($p) or intval($id) no longer validates $p or $id: ../../x/log.txt and 1 OR 1 pass it.

v0.5.8Coming soon

Sees further

  • A new rule tier, reference, for a rule about how a call is made rather than about input reaching it (only a rule with sources = [] may have it). app_code_audit and chat list its findings after the others, marked as reference; the daily report gives them one line with their count. They are never pushed and never given to attack detection. The info and alert tiers are unchanged.
  • block_ip reads the server's DNS servers and default gateways (/etc/resolv.conf, systemd-resolved's copy, /proc/net/route, /proc/net/ipv6_route) through the host source, as the SSH sessions it also checks: a replay or another host's survey is never answered by the machine running it. One of them there but not read now refuses the block (state_error); before, the error was dropped and the list taken for empty, so the gateway or DNS server could be blocked. A file absent (no systemd-resolved, no IPv6) is still no entry.
  • app_code_audit, app_vulns (lock files and site-packages) and the WordPress plugin list walk the host source, as the web roots they start from already came from it: a replay or another host's survey is never answered by the machine running the check. Links are still not followed, a file is read only if it is the one the walk saw, and the limits are the same. A web root or app path there but not read (no permission, or a replay that lacks it) is now listed in the audit's not_checked; before, it was audited as an empty folder. A replay of a fixture recorded before this version says every such path not read, never "not there".
  • package_vulns reads every page of OSV's answer: OSV gives at most 1000 advisories a query and names the next page; only the first was read, so the kernel's list stopped at 1000 (on Ubuntu 24.04, 383 CVEs fewer than another scanner found). Past 10 pages a package's rest is said in partial, never cut quietly.
  • package_vulns on Ubuntu: a USN covers every release it fixed, and its aliases name CVEs some other release has only (USN-7980-1 names CVE-2025-11187, which OSV has for 25.10 and 26.04, not 24.04). Of a USN only the CVEs OSV also lists for that package on the host's release count now, so a CVE of another release is no longer marked actively exploited (KEV) on this host, nor counted on the surface, nor taken for a CVE OSV already reports when a third-party PHP or nginx is compared with upstream. A USN whose package has no CVE-named advisory to tell its CVEs' release by is counted in kev_unchecked and named, never dropped quietly.
  • Windows: Shentu's own files opened without following a link (the dispatch log, the AI budget reservations, the auto-incident and audit locks) are checked and used through one handle, opened not following a symlink or junction. Before, the file was looked at, then opened by its name, and the two compared in a way that cannot tell on Windows: a file swapped for a link in between was opened through the link. A deduplicated file (Windows Server Data Deduplication) is still opened; another kind of reparse point is said, not opened.
  • Windows: site_profile, the processes, listening ports, accounts and SSH tools, log_search and the Python site-packages check go by the host read (Windows or not), as the macOS ones do, not by the machine running the check. Replaying a Windows host's reads, or checking one from another machine, no longer gives the Linux answer, and site-packages matches a Windows venv's RECORD paths (without case, as Windows names files, and with an old pip's \): a genuine .pth a package's RECORD lists is no longer reported as unknown. On a Windows host where Apache shows (an httpd.exe process or service, C:\Apache24\conf\httpd.conf or C:\xampp\apache), site_profile's risks list one more unchecked risk, unchecked:notyet:apache:windows: Apache there is not checked yet, so CVE-2026-119618 (HTTP/2) is not evaluated. The daily report lists it under "Not checked by this release yet", not under the missing-permission heading.
  • app_vulns and the daily patrol check the Python packages in Docker images against OSV as PyPI, with the CISA KEV mark. They are read from Docker's overlay2 image store on disk; no container is started and the daemon is not asked. Each tagged image's layers are stacked as overlayfs stacks them: a higher layer's file replaces a lower one's, a deleted file (a whiteout) removes only that name in its own folder, and an opaque folder hides the lower layers' files in it. Until now a package inside an image was not checked at all. A store that is there but could not be read (not root, a file not read, past the bounds of 50 images, 200 layers or 200,000 files) is reported as not checked, each such line of the daily report on its own; a host with no Docker store says so apart. The store's folders are not followed when they are symlinks, and when the run is stopped the images left are said not checked. Images in containerd's store (new Docker releases keep them there by default: /var/lib/containerd, or containerd-snapshotter turned on in daemon.json) are not read by this release: partial says so rather than "no images", and the daily report lists it under what this release does not check yet. The store is read only when the host read is this machine itself: a replay says the images were not checked. A .pth in an image is never taken as a tool's own.
  • package_vulns' overview tells how many of the vulnerabilities a fix is known to be out for (fix_available, also per package) and how many it is not known for (fix_unconfirmed). A fix is known when the advisory is a distribution's update notice (DSA, DLA, USN, RLSA, ALSA, SUSE-SU) or an ALAS. A php.net or nginx.org entry is counted in fix_available too: the fixed release is out upstream, though the repository the package came from (sury, for one) may not have packaged it yet. The rest, such as a CVE entry of Debian's or Ubuntu's tracker, are unconfirmed: the overview does not fetch each advisory to tell, and fix_note says that unconfirmed is not "no fix". Until now the count mixed them; package set still gives each one's fixed_version, without the counts.
  • site_profile on Linux and macOS says two more risks. sudo:nopasswd (a warning): sudoers lets someone run every command with no password: ALL anywhere among the commands a NOPASSWD tag covers (it holds up to a PASSWD tag), a command alias that is ALL or cannot be told, a command whose path is a folder or holds a wildcard (/usr/bin/, /usr/bin/*: sh among them; a wildcard in the arguments only is not), a command masked as a secret would be, or Defaults !authenticate for everyone, a user or a run-as account; in any sudoers file, for a group or ALL. The one exception is the cloud image's default user: such a rule in /etc/sudoers.d/90-cloud-init-users (that path only) for cloud-init's default_user (read from /etc/cloud/cloud.cfg and cloud.cfg.d/*.cfg, not user-data; one set in a way not read, such as {name: x}, a quoted key or JSON, is none) alone is sudo:nopasswd:cloud-init (info, in the report only), whose text says it is safe only while that user logs in with a key alone. NOPASSWD for some commands only, or Defaults!cmd !authenticate for some, is sudo:nopasswd:some (info). Each rule is listed with what it runs and the account it runs as. The rules are read through every #include/@include and includedir as sudo reads them (names with a dot or ending in ~ skipped). A file not read, or sudoers from sss or ldap, is said as unchecked:sudoers, never taken for no such rule. A recording keeps sudo's tags only in sudoers files (/etc/sudoers, /etc/sudoers.d/* and what they include), in their rule lines, where the word after the tag is a command (ALL=NOPASSWD: /path, (root) NOPASSWD: DEPLOY, sudoedit, an option), so a replay reads these rules as written; everywhere else the secret masking is as before, and now also masks the value in (x) PASSWD: !<password> and FOO: PASSWD: ALL-<password>. reboot:pending (a warning): an update waits for a reboot, its old kernel or libraries still running. On Debian and Ubuntu it is /run/reboot-required (with the packages it names); elsewhere a kernel in /boot newer than the running one of the same flavor (+debug, UEK and the distribution's own kernel compared apart). A running kernel not in /boot (a container) is not compared.
  • file_changes and log_search's hard-link check read the host as the other checks do, through the host source: a replay or another host's survey reads that host's files, not the machine running the check, a Linux or macOS host's recording read on a Windows machine too (its paths keep their "/": the walks, the log allowlist, the site-packages search, the WordPress plugin search, app_vulns' and app_code_audit's path argument, and the audit resuming where it stopped spell them as the host does). The host source's file details now carry the status-change time (ctime, which file_changes counts as before: a file whose mtime was set back still shows) and the hard links; these checks are made on Unix only (on Windows the details say they do not apply, never 0).
  • A file app_code_audit, app_vulns' lock-file search or the WordPress plugin search would read that is not a regular file (a FIFO, a device, a cloud or HSM placeholder such as a OneDrive file not on the disk) is said rather than skipped quietly: the audit's not_checked and app_vulns' partial count them and name the first three; a plugin's .php file of that kind is named among what was not read when no header was found. A link is not followed, as before, and not counted.
  • A refused connection to a model outside this host is said "connection refused" on Windows too; it was said "connection failed" there (Windows gives WSAECONNREFUSED).
  • sudo's risk texts say each rule by its file, whom it is for, what it runs and as whom (/etc/sudoers.d/90-admins: %admin (every command, as root)), not by its line: a pushed text is no longer masked to [REDACTED]. A secret in a command's arguments or a run-as list, written as key=value or in one of the forms below, is masked in the text itself, so the survey's own output (onboard, the saved profile) does not hold it either.
  • The secret masking (fixtures, logs, what the model is given, Windows checks' command lines) now also masks a password given as a command's own argument: -p<secret> after a program of the mysql family (mysql, mysqldump, mysqlcheck, mysqladmin, mysqlbinlog and the others, mariadb and its tools, in any case, .exe too), --password <secret> or --passwd <secret> as the next argument, and curl's or wget's -u user:<secret> / --user user:<secret>; also in a JSON argv on one line (["mysqladmin","ping","-p<secret>"], "--password", "<secret>", "-u", "user:<secret>", as docker inspect and a healthcheck write them). key=value was masked before. A process's command line (/proc, ps, Windows') is masked argument by argument, so a ;, | or & in a password is masked with it; in other text (a log line, a shell's history) a command reaches only to an unquoted ;, | or &, so a git refspec (git push -u main:main) or tar -pcf after it is left. -P 3306, docker run -p 8080:80, the mysqld and mariadbd daemons' -port=, --password-file=/path and a bare -p are left as they are.
  • The host survey parses commands' output as written, not masked first (packages and rpm vendors, the firewall's rules, macOS's platform, accounts, processes, listeners, pf and protections): an unclosed private key marker in one process's path, or in an iptables rule's comment, no longer hides the processes or rules after it. The output is parsed as written; the fields kept from it are masked, and so is a command's error text in a message. nginx's and PHP's package queries are read masked (the package manager's text).
  • The cryptominer check matches a process's command line as written (Linux, macOS, Windows): a renamed miner whose options follow a password the mask takes whole (mysql -p' -o stratum+tcp://… ') is still found. Its evidence, and what the model is given, stay masked.
  • Attack detection reads PHP's error logs and journald's messages as written, not masked first: a request's text echoed before PHP's location (an unclosed private key marker) no longer takes the location with it, so the sink keeps its error-log evidence. The events keep only times and locations, and nothing from them is output.
  • On Windows, log_search masks a field's value on its own before its name and value together: a value starting with a program (CommandLine=mysql -u root -p<secret>) is masked; masked only as Name=value, the = before it hid the program.
  • On Windows the checks read a service's command line, a registry string and a scheduled task's XML as written, not masked first: an unclosed private key marker in a service's path, a home's path or a task's description no longer hides an unquoted service path, a startup folder or the task. What they output stays masked.
  • The site's home page: a section that rises into view (the tally, open source, the latest release with the river) no longer stays blank when the page is reached in its middle, as from a link to an anchor, by going back to the page, or by a jump. A section shows once any part of it is in the window; sections in the window when the page loads, and every section on a page opened at an anchor, show at once.
  • PHP rules follow extract() of an array not written out. After extract($args), extract($_POST) or extract(wp_parse_args($atts, [...])) (which keeps every key of $atts), each variable of the function may hold that input until it is assigned again: one defined before (a template loader's $template_name, overwritten by extract($args)) and one never assigned ($team_id after extract($opts)). Before, no variable was set, so a shortcode's attributes passed this way reached include or call_user_func() unreported (CVE-2023-6996). extract(shortcode_atts($defaults, $atts)) sets the keys of $defaults only, and never $defaults itself; EXTR_SKIP and the EXTR_PREFIX_* flags overwrite nothing; a property of a value extract() set ($wpdb->prefix after global $wpdb) holds no input, an index of it does. The flags count as PHP reads them: EXTR_SKIP and EXTR_PREFIX_SAME overwrite nothing, EXTR_IF_EXISTS overwrites but creates nothing, EXTR_PREFIX_ALL and EXTR_PREFIX_IF_EXISTS set only prefix_ names (any such name when the prefix is not written out). A variable extract() creates around a closure is seen in it only through its use (...), and its parameters are the caller's values.
  • PHP rules: after preg_match($p, $s, $m), preg_match_all(), parse_str($q, $out) or exec($c, $output), the variable written by reference is the call's, so a value extract() set there before is gone; whether it holds the subject's input is still not followed, but a variable that is the subject itself (preg_match($p, $m, $m), parse_str($q, $q)) keeps what it held. A catch (E $e) variable is the exception, not what the name held before.
  • PHP rules: WordPress's $wpdb kept in a property ($this->wpdb = $wpdb, $this->db = &$wpdb, self::$mysqli =& $wpdb) is $wpdb wherever the same file queries through it ($this->wpdb->get_results(...)), so request input concatenated into such a query is reported; before, only $wpdb itself was a sink. The class (or a trait of the file it uses) must show the assignment: a property named wpdb or db alone, one set in another file (a parent class), or one another class of the file gives $wpdb is not read as $wpdb.
  • PHP rules: request input passed to $wpdb->prepare() for a %s placeholder written inside backticks, where the value is a column or table name (also a numbered %2$s), is reported (php-sqli-prepare-identifier): prepare() quotes the value as a string, which does not protect an identifier. Before, prepare() counted as escaping every value. A %s between quotes, standing alone, after ORDER BY or in LIMIT, %d and %i are not reported.
  • PHP rules: input put in array(...) and passed to another function keeps its input, as [...] did (edit_status(array($_REQUEST['id']))); before, array(...) read as a call the engine does not know, so the input did not cross into that function's sinks.
  • Python rules: Tornado request arguments (self.get_argument(), self.get_query_argument(), self.get_body_argument()) passed to self.redirect() are reported; before, neither the arguments nor self.redirect() were read by the redirect rule.
  • PHP rules: PSR-7 request input ($request->getQueryParams(), ->getParsedBody()) passed to a redirect response (new RedirectResponse($url)) is reported.
  • PHP rules: a Symfony request's body ($request->getContent(), $request->toArray()) written into SQL in the same function is reported, an ORDER BY column too.
  • PHP rules: a cell read with fgetcsv(), as from an imported CSV file, and passed to unserialize() without ['allowed_classes' => false] is reported.
  • A new JavaScript rule, js-file-upload-client-name-write: an upload written with fs.createWriteStream(), fs.writeFile(), fs.writeFileSync() or fs.promises.writeFile() under the name the client sent (multer's file.originalname) is reported. express-fileupload's .name is not read.
  • Route models can name the hook a call registers (hooks): the call counts only when its first argument is one of those names, written out as one string; a variable, a constant or a joined string there does not count. path and hooks cannot be used together.
  • PHP rules: the editor data Elementor passes to elementor/editor/after_save callbacks (the second parameter, every element's settings, which contributors and up write) is request input. Before, a URL read from a widget's settings there and fetched (getimagesize()) was not reported.
  • bench: the baselines are rerun on the product scan path (baseline.md for cves, and now baseline-holdout.md, baseline-cves-ts.md); the one before was the first run, on 59 cases, scanned file by file.
  • php-nosqli-mongo-query and the CodeIgniter, Doctrine, Drupal, Joomla and Yii SQL rules: a method sink ($Db->find(...), ->where(...)) reached from another file is not reported when the project's own classes declare a method of that name and nothing app_code_audit reads names the library: not its PHP code, a string in it, composer.json, composer.lock, nor the name of a package under vendor/ (whose files it does not read). The call is the project's own (a WordPress plugin's SQL helper). Before, a method of that name counted on any object. It stays reported when anything names the library, when no class of the project declares the method, and whenever app_code_audit left a file out: a folder it skips (node_modules/, .git/), one more than 8 levels deep, a rule-language file over 1 MiB or not readable, more than 20,000 files, or a walk cut short. A call found in the file it is written in is reported as before.
  • php-deserialization-wp-maybe-unserialize: an argument that is an array on every path is not reported (maybe_unserialize(array('fields' => $_POST['f'])), an array written by key, explode()), also when a function of the code's own passes its parameter on as is: maybe_unserialize() unserializes strings only and returns an array as is. Before, the input in the array counted. One value of the array, a string made from it, and a path where the input arrives as a string are still reported, and so is an array the code may write some way the engine does not follow: a variable of the global scope or declared global, a file with $$name, ${...} or $GLOBALS, or one passed whole to a method, a computed callee, a PHP function that takes it by reference, or a function the project does not declare (WordPress's own, but for a few that take it by value) or declares with a parameter by reference.

Sees more precisely

  • A Debian or Ubuntu package held with apt-mark hold (dpkg state hi), or marked for removal but still installed (ri, pi), is checked as an installed one is. The package list went by dpkg's ii only, so a held package was neither checked nor said (the v0.5.7 known issue). A package dpkg has on the disk but not installed in full marks the package list partial, named there with its state (20 at most, the rest counted). One whose files are all unpacked (unpacked, half-configured, triggers awaited, triggers pending) is checked at the version dpkg records. One half-installed, or in a state not read, is not checked: it is listed in packages_not_checked with its state, before the ones with only their configuration left (config-files), which are listed only. The first 20 are listed, the rest counted in packages_not_checked_more. The tool's description says both fields.
  • cvebench scans as app_code_audit does by default (-scanpath product): each file on its own, then the calls across files, merged. Before, it decided each flow with the calls across files (Project.Scan, now -scanpath project), so a check written in another file took a finding away that app_code_audit still shows. The rules are the same; the bench's fixed false positives usually rise, closer to what a user sees (measured on v0.5.8's cases: nothing reported fewer). The report's header names the scan path and the project caps.

Known issues

  • A command's own password is not masked when it is only JSON punctuation (, : { } [ ] and spaces), past a space in it (a command line joins argv with spaces; quoted in a shell line it is masked whole), past an unquoted ;, | or & in a log line or a shell's history, in a JSON argv printed over several lines or after a string holding ], or given to another program's option (sshpass -p, redis-cli -a, ldapsearch -w, smbclient -U user%<secret>, mongosh -p, htpasswd -b, curl's --pass and -E cert:<secret>).
  • Some checks still read texts masked when read in: on Windows event data (each field masked on its own; log_search's text of an event is masked field by field).
  • A secret whose name and value an event gives in two fields (a name in one, the value in the next) is not masked in log_search's text; Windows' own events give none so (CommandLine, ImagePath and ScriptBlockText are one field each).
  • A user's name of mysql given to an option in text (a log line, a shell's history, a cron line: --user mysql -p5432, psql -U mysql -p5432) is read as the program, and the -p after it is masked (a process's command line, judged argument by argument, is not); a file named .mysql (psql -f backup.mysql -p5432) is read so in text and in a process's command line alike.
  • log_search matches the masked text: what the mask covers cannot be found. A pattern matched against the text as written would tell, match by match, what a masked secret is.
  • A recording (a fixture) holds the masked text only, so a check replayed from it can decide otherwise than on the live host: the cryptominer check, on options the mask covered, and attack detection, which can have less error-log evidence (an error log or journald message whose location the mask covered).
  • A redirect target checked in another file (a Tornado base class's self.sanitize_next_url()) is still reported: app_code_audit reads each file on its own first, and that finding stays when the calls across files show the check.
  • js-file-upload-client-name-write reads no allowlist as a check: an upload written under the client's name after its extension or MIME type was checked against a list (express-cart 1.1.7) is still reported.
  • Input handed to a route generator that builds a path on the site is still reported in a redirect (PSR-7's urlFor(), Flarum's $url->to(...)->route(), Tornado's reverse_url()).
  • fgetcsv(): a row assigned in a while condition (while (($row = fgetcsv($h)) !== false)) is not followed into the loop, so that usual way of reading a CSV file is missed. A CSV file the application ships itself is reported as well.
  • A value escaped with a database library's ->escape() and written inside quotes is still reported (php-sqli-string-concat): the rule does not read ->escape( as a check, as some libraries' escape adds no quotes and a numeric position is left open. A Symfony body now reaches it too.
  • A Symfony body decoded with json_decode() and passed to another function loses its input there, so a field decoded in a controller and written into SQL in another class is missed.
  • After extract() of input, a property of a variable it set ($cfg->path) reads as no input: extract() of request data sets strings and arrays. extract((array) json_decode($in)) and extract(get_object_vars(json_decode($in))) can set objects whose properties are input, and these are missed.
  • A reference rule misreads a few forms. A command written out in full is still reported when it is split into adjacent string literals (os.system('ls ' '-l'), which Python joins into one) or joined from a list of literals (' '.join(['ls', '-l'])). An attribute receiver (h.env.from_string(s)) is known by its name only, even where the file assigns it (h.env = Engine()). o.system(cmd) after import os as o, and a function imported under another name (m(x) after from hashlib import md5 as m), are not reported.
  • On a non-Windows machine replaying a Windows host's recording, the code audit's ASP check, its web-root ACL check and its case-insensitive path comparison are not turned on yet, and app_vulns' and app_code_audit's path argument is refused unless it is one of the app paths exactly (v0.5.9).
  • A route model reads a handler only in the file that registers it: an elementor/editor/after_save callback written in another file than its add_action() (the hook in the main plugin file, the function in an include) is not read as one, so a fetch there is not reported. The other route models share the limit.
