New rules enshrined

v0.2.52026-11-13

Sees further

  • app_code_audit follows calls across files: input read in one file and used in a sink of another is reported at the sink, with the file it came from.
  • Framework route models: the parameters of WordPress hooks, shortcodes and REST routes, Laravel routes, Django URLs, Flask and FastAPI views and Express handlers are input, also when the route is registered in another file.
  • New rule classes: LDAP injection, NoSQL operator injection, dangerous file uploads, weak cryptography and hard-coded credentials; TypeScript files are checked with the JavaScript rules.
  • Audits keep their results between runs, so a large application is covered over a few patrols instead of one.
  • An audit spread over several runs can still report a few findings that differ from one run without a time limit; a fix is in progress.
  • js-cmdi-spawn-shell still reports spawn() and execFile() calls whose command and arguments are fixed when only the options (such as cwd or env) carry request values.
  • In $wpdb->prepare()/->prepare() formats, a placeholder list built by a callback that returns a constant (implode(',', array_map(fn($v) => '%d', $ids)), or the same with function ($v) { return '%d'; }) is still treated as input and reported when $ids comes from the request. array_fill(0, count($ids), '%d') and sizeof() are recognised. Reading a callback's return value needs an engine change (planned for v0.2.6).

Sees more precisely

  • Fewer false positives: wp_send_json output, JSON_HEX_TAG data blocks, MongoDB queries on objects that are not collections, and Django _meta.get_field checks.
  • php-deserialization-phar-wrapper reports filesize() on an upload's temporary path in WordPress's REST attachments controller, a false positive: the path is PHP's own, but the engine cannot yet tell an upload's tmp_name from its client-set name.
  • js-nosqli-mongo-query reports TypeORM repository calls on SQL databases (find/findOne whose options hold a where built from request values, e.g. n8n's public API and credential lookups) as MongoDB queries; TypeORM sends those values as SQL parameters, so these are false positives, to be told apart by a TypeORM-aware receiver check in v0.2.6.
  • js-xss-response has no Server-Sent Events exception: res.write("data: " + value) in a text/event-stream handler is reported as XSS (a false positive), and nothing is missed because of SSE; telling streams apart by the handler's Content-Type is planned for v0.2.6.
  • ->get_settings() counts as Elementor widget input in every class, so WP_Widget::get_settings() and WooCommerce WC_Settings_Page::get_settings() values (saved by administrators) are reported too. Limiting the source to classes extending \Elementor\Widget_Base needs class-scoped sources in the engine (planned for v0.2.6). Values read through ->get_settings() can also be followed into WordPress admin field definitions and into a few SQL sinks that are already guarded (an isset() check, or a value bound through $wpdb->prepare() inside ORDER BY FIELD()), which gives extra false positives there. Narrowing the source to Elementor widgets is planned for v0.2.6.
  • python-path-traversal-send-file reports zipfile.ZipFile(request.files[...]), which opens the uploaded stream rather than a path, a false positive. Telling a request's file stream from a client-set file name inside one argument needs an engine change (planned for v0.2.6).

Runs lightly

  • The audit sizes itself to the server: heap at most min(1 GiB, 25% of available memory, 50% of the service's cgroup), workers from the CPU count and the load.
