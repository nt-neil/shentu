v0.3.0即將發布

看得更遠

  • 支援 Windows Server 2022 與 2025，已在實機（GitHub 的 Windows runner）上驗證（amd64，另建置 arm64）：Windows 收集器只透過 Windows API 讀取主機（登錄檔、服務、程序、通訊埠、帳號、排程工作、事件記錄、WMI 與防火牆），不用 PowerShell，也不執行外部指令。
  • Windows 檢查：自動啟動項目（Run 機碼、服務、排程工作、啟動資料夾、WMI 事件訂閱）、未啟用 NLA 的 RDP、SMB 簽章與 SMBv1、不安全的 WinRM、防火牆設定檔、Defender 狀態與排除清單、登入失敗與記錄被清除。
  • 依 Microsoft 每月安全性更新（MSRC）比對缺少的 Windows 更新，並以 CISA KEV 清單標出已被 利用的漏洞、優先列出。
  • IIS：從 applicationHost.config 取得網站根目錄；程式碼稽核會讀取 ASP 與 ASP.NET 頁面，找出 webshell 與上傳目錄裡的腳本，UTF-16 頁面也包含在內。
  • 兩個 Windows 服務：Shentu（巡邏）與 ShentuBot（Telegram），從 %ProgramFiles%\Shentu 以 shentu service install [--bot] 安裝；設定與狀態放在 %ProgramData%\Shentu，只有 SYSTEM 與 Administrators 能存取。
  • ssh_logins、processes、accounts_audit 與 log_search 工具可在 Windows 使用（登入 事件、程序清單、本機帳號、事件記錄）。
  • SSH 登入沒成功的紀錄改為先讀 journald：ssh 與 sshd 單元的標記由 journald 自己填入，本機用戶不能偽造。journald 不存在、讀取時間到了上限（60 s），或沒有 sshd 紀錄時，才改讀文字紀錄檔（auth.log、secure）。本機任何人都能用 logger 寫入一行 sshd 紀錄，所以這時 auth_events 標為 partial，原因是新的 unverified_source，多次試圖登入的告警也會附註來源未驗證。不是 root 的用戶沒有權限看系統紀錄時，不再當成「沒有登入沒成功」。
  • Windows 版只讀不寫：不支援 block_ip 與 unblock_ip。
  • Windows Server 2019 為 best effort：預期可用（相同的 Windows API，build 17763），但沒有 實機驗證。
  • shentu setup 還不能在 Windows 上執行，設定需要手動撰寫。
  • Windows 執行檔沒有程式碼簽章，也沒有 MSI；SmartScreen 或防毒軟體可能發出警告。

  8. 2026-11-13

    增祀 v0.2.5

    • app_code_audit 會跨檔追蹤呼叫：在一個檔案讀進來、在另一個檔案的危險呼叫用掉的輸入，會在危險呼叫處報出，並標明來源檔案。
    • 框架路由模型：WordPress 的 hook、shortcode 與 REST 路由，Laravel 路由、Django URL、Flask 與 FastAPI 的 view，以及 Express handler 的參數都視為輸入，路由註冊在別的檔案也一樣。
    • 新的規則類別：LDAP 注入、NoSQL 運算子注入、危險的檔案上傳、弱加密與寫死的憑證；TypeScript 檔案用 JavaScript 規則檢查。
    • 稽核結果會在多次執行之間保留，大型應用程式分幾次巡邏就能掃完，不必一次跑完。
    • 稽核依伺服器調整自己：記憶體上限取 min(1 GiB、可用記憶體的 25%、服務 cgroup 的 50%)，並行數依 CPU 數與系統負載決定。
    • 誤報更少：wp_send_json 的輸出、JSON_HEX_TAG 的資料區塊、不是 collection 的物件上的 MongoDB 查詢，以及 Django 的 _meta.get_field 檢查。
    • 分成多次執行的稽核，仍可能有少數結果和不限時間的單次執行不同；修正進行中。
    • php-deserialization-phar-wrapper 會把 WordPress REST attachments controller 裡對上傳暫存路徑做的 filesize() 報出來，這是誤報：那個路徑是 PHP 自己產生的，但引擎還分不出上傳檔的 tmp_name 和客戶端填的 name。
    • js-nosqli-mongo-query 會把 SQL 資料庫上的 TypeORM repository 呼叫當成 MongoDB 查詢，也就是 options 的 where 由請求值組成的 find/findOne（例如 n8n 的公開 API 和查 credential 的地方）。TypeORM 會把 這些值當成 SQL 參數，所以這些是誤報；v0.2.6 會改用能認出 TypeORM 的 receiver 檢查來區分。
    • js-cmdi-spawn-shell 在指令和參數都固定、只有 options（例如 cwd 或 env）帶到請求值時，spawn() 和 execFile() 仍然會被報出。
    • js-xss-response 不再對 Server-Sent Events 例外：在 text/event-stream 的 handler 裡寫 res.write("data: " + 值) 會被報成 XSS（誤報），但不會因為 SSE 而漏報；依 handler 的 Content-Type 分辨串流的功能排在 v0.2.6。
    • ->get_settings() 在任何 class 裡都會被當成 Elementor widget 的輸入，所以 WP_Widget::get_settings() 和 WooCommerce WC_Settings_Page::get_settings() 回傳的值（由管理員存入）也會被報出來。要把來源 限定在繼承 \Elementor\Widget_Base 的 class，引擎得支援依 class 限定 source，預定 v0.2.6。經由 ->get_settings() 讀到的值，也可能被追進 WordPress 後台的欄位定義，以及少數已經有防護的 SQL 位置（例如先用 isset() 檢查，或在 ORDER BY FIELD() 裡用 $wpdb->prepare() 綁定），因此在這些 地方會多出誤報。v0.2.6 會把這個來源限縮到 Elementor 元件。
    • 在 $wpdb->prepare()／->prepare() 的格式字串裡，如果佔位符清單是由只回傳常數的 callback 產生 （例如 implode(',', array_map(fn($v) => '%d', $ids))，或改用 function ($v) { return '%d'; } 的寫法），只要 $ids 來自請求，仍然會被當成輸入報出來。array_fill(0, count($ids), '%d') 和 sizeof() 的寫法已能辨識。要讀出 callback 的回傳值需要 改引擎，預定 v0.2.6。
    • python-path-traversal-send-file 會把 zipfile.ZipFile(request.files[...]) 報出來，這是誤報：它開的是 上傳的檔案串流，不是路徑。要在同一個參數裡分出請求的檔案串流和客戶端填寫的 filename，需要改引擎，預定 v0.2.6。
