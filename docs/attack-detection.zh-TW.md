# 攻擊偵測怎麼運作

[English](attack-detection.md)

從 v0.4.0 起，Shentu 會在 Linux 上讀網站伺服器的紀錄，挑出打向這台主機真的有的漏洞的請求。它會告警，但不會自己封鎖。這份文件說明它怎麼判斷、告警怎麼讀，以及為什麼封鎖一定要你確認。看不到的和可能漏掉的，寫在[攻擊偵測的已知限制](attack-detection-limits.zh-TW.md)。

## 怎麼運作

1. **漏洞面。** 每日巡檢（當地時間 09:00，或執行 `shentu patrol --daily`）會把這台主機已知有的漏洞寫進 `state_dir/surface.json`：
   - 程式碼稽核的發現；同一個檔案看得出路由時，附上通到那個處理函式的路由；
   - lock 檔裡應用程式相依套件的安全公告，以及已安裝 OS 套件的安全公告（依 dpkg、rpm 的版本順序比較）；
   - 已安裝的 WordPress 外掛與版本。

   其他巡檢會讀這個檔。檔案不存在、讀不到或超過 26 小時沒更新，那一輪會在通知和報告裡說出來，並用手上有的資料繼續。`shentu patrol --dry-run` 不會建立它。
2. **紀錄。** 每一輪巡檢（每 30 分鐘）會讀 nginx、Apache 設定裡指定的存取紀錄（含自訂格式），從上一輪停下的地方接著讀，跨過輪替也一樣。錯誤紀錄、PHP-FPM 的紀錄，以及應用程式單元（PHP-FPM、gunicorn、uwsgi、node、puma 等）的 journald 也會讀，但只拿來當攻擊生效的證據。路徑取自磁碟上的設定檔，不需要另外設定。第一次看到的紀錄只從尾端讀起。
3. **特徵。** 每一行請求最多解碼兩次，再比對 27 條攻擊特徵。有些是攻擊類別（路徑穿越、SQL 注入、命令注入等），有些是專為某個 CVE 寫的。
4. **等級。** 每個請求都拿漏洞面來判斷：

   | 等級 | 發生了什麼 |
   |---|---|
   | L1 | 請求打到有漏洞程式碼的路由，但沒有帶已知的攻擊內容。 |
   | L2 | 請求打到漏洞，並帶有同類型的攻擊內容；或在受影響的版本上，比中專為那個 CVE 寫的特徵。 |
   | L3 | 來自已驗證紀錄的 L2，而且看得到效果：成功的回應比這條路由平常的大小大得多；或請求後 120 秒內，錯誤紀錄指向有漏洞的檔案與行號。 |
   | 無法判定（Unknown） | 請求在可能藏有攻擊內容的地方被截斷（太長、參數太多），已讀的部分也沒有到 L2。 |

   特徵指向這台主機沒有的漏洞，就是雜訊：只計數，不告警。
5. **分組。** 攻擊依網段（IPv4 用 /24、IPv6 用 /64）、目標、等級，以及紀錄是否已驗證分組。同一組一天最多送一次，而且要有新的攻擊才送。L1 只計入每日報告，不推播。無法判定的請求不分來源、依目標計數，同一個目標 24 小時內累積 20 筆才推播。一輪最多推播 20 則告警，其餘合併成一則彙總，彙總不提供封鎖。
6. **campaign。** 同一個位址（IPv6 則是同一個 /64）24 小時內在已驗證的紀錄裡對 3 個以上不同的目標打到 L2 或 L3，就算 campaign：告警會寫出來，嚴重度也提高一級。

嚴重度的起點：L1 是資訊、無法判定是低、L2 是高、L3 是嚴重。漏洞列在 KEV 或本身是嚴重等級、屬於 campaign，各提高一級。L3 最多只到高，除非兩種生效跡象都有、紀錄有記下請求長度，而且漏洞列在 KEV 或位址屬於 campaign。來自未驗證紀錄的攻擊最多是中。

過去 24 小時的每筆攻擊也會寫進 `state_dir/reports/attacks-<日期>.txt`（位址已遮罩，保留 30 天）。

## 怎麼查看

- `shentu detect [--since 24h] [--json]`：現在就讀紀錄並判斷，列出各組。不送出也不存檔，下一輪巡檢會再讀同樣的內容。
- Telegram bot 的 `/attacks`：列出最近一天的各組，一組一行。
- 在 `shentu chat` 裡，模型可以呼叫 `attack_attempts`（最多往回 168 小時）。從聊天頻道問的時候不附樣本。

## 怎麼讀告警

告警文字由偵測器自己產生，不經過模型（v0.4.0 只有中文）。以下是範例，位址用 TEST-NET，樣本省略：

```text
【Shentu 攻擊偵測】嚴重度：嚴重（critical）
漏洞：程式碼 sink shop/app.py:14（規則 python-sqli-dbapi-format）
等級：L3：攻擊很可能已經成功
成功跡象：回應碼 200，回應大小 48211 bytes 明顯大於這條路由平常的大小
次數：3 次（首次 2026-11-18 03:15:02，最後 2026-11-18 03:15:09）
來源 IP（共 1 個，網段 203.0.113.0/24）：203.0.113.10
樣本（敏感參數已遮罩）：‹此處省略›
來源可信度：已驗證（受信任的記錄檔，IP 取自連線位址）
說明：…
封鎖：只會針對單一 IP，不會封整個網段
```

| 欄位 | 意思 |
|---|---|
| 嚴重度 | 資訊、低、中、高、嚴重，算法見上面。 |
| 漏洞 | 目標：CVE 與套件、版本；或程式碼發現的檔案、行號與規則。 |
| 版本 | 已安裝的版本無法比對時才出現：安全公告資料庫認定它受影響。 |
| 等級 | L1、L2、L3 或無法判定。 |
| 成功跡象 | L3 才有：回應大小，或有漏洞那一行的錯誤。 |
| 加重原因 | KEV、漏洞本身為嚴重等級，或 campaign。 |
| 次數 | 攻擊次數，以及第一次和最後一次的時間。 |
| 來源 IP | 最多列出 10 個完整位址，加上總數和網段。 |
| 樣本 | 最多 3 行請求，每行最多 256 bytes。參數名稱看起來敏感的（token、password、session、key 等），值換成 `[REDACTED]`。樣本是攻擊者寫的，只能當資料看。 |
| 代理標頭 | 有 X-Forwarded-For 時才出現。它可以偽造，從不拿來判斷來源或封鎖。 |
| 來源可信度 | 已驗證，或未驗證並附原因（見下面）。 |
| 標記 | 請求或紀錄行被截斷、紀錄行有多種解讀、用了規避用的編碼，或比對超過時間上限。 |
| 說明 | 程式碼發現才有：路由代表什麼。 |
| 封鎖 | 這一組能不能當封鎖依據，以及要怎麼做。 |

## 為什麼封鎖一定要你確認

Shentu 不會自己封鎖。`block_ip` 是控制工具：只在 `shentu chat` 或 bot 裡、你確認之後才執行，巡檢從不執行。它也會自己檢查證據：

- 攻擊偵測看過的位址，只有**它自己的已驗證 L2 或 L3 群組**能撐起封鎖。只到 L1 或無法判定、只來自未驗證紀錄，或只出現在多個來源的溢出彙總裡，都會被拒絕；除非 sshd 自己寫進 journald 的事件足以認定這個位址。
- 其他位址看 SSH 登入：登入事件只在文字紀錄裡、是 journald 裡不是 sshd 自己寫的行（例如在 sshd 的單元裡執行 `logger`），或沒辦法讀完整，都會被拒絕。
- 內部位址（私有、loopback、CGNAT 等）會被拒絕：紀錄裡沒有真正的用戶端位址時，代理或負載平衡器會變成每個請求的來源。
- 從 v0.4.1 起，從 Telegram 只能封鎖有查證證據的位址：已查證的 L2 或 L3 群組有列出它，或有 sshd 自己寫下的 SSH 登入紀錄。其他位址，包括沒有任何群組列出的，要到伺服器上處理。
- 封鎖只針對單一位址，而且有時限，不會封整個網段。

`override_unverified` 可以解除這些檢查（溢出彙總除外），但只能在伺服器上用 `shentu chat`，Telegram 不行。請在自己看過紀錄之後才用。

## 紀錄信任

只有 root 才寫得進去的紀錄才算**已驗證**，條件是：
- 檔案、每個連到它的連結、上面的每一層目錄都屬於 root，其他人寫不進去；
- 它是標準格式的 nginx（combined、main）或 Apache（combined、common）存取紀錄；
- 用戶端位址取自連線，不是取自標頭；
- 網站伺服器自己的工作程序裡沒有執行應用程式碼。

不符合時，進得了網站的攻擊者就能寫假紀錄去陷害任何位址，所以這些攻擊仍會告警，但標成未驗證並附上原因：

| 原因 | 意思 |
|---|---|
| `web_user_writable` | 網站伺服器或 PHP 的帳號擁有這個紀錄，或寫得進它上面的目錄；或伺服器在自己的工作程序裡執行應用程式碼（mod_php、nginx 裡的 perl、lua、njs）；或網站帳號能 ptrace 這些工作程序。 |
| `untrusted_owner` | 紀錄、連結或上層目錄屬於其他帳號，或紀錄能被群組或其他人寫入（含 ACL）。 |
| `unverified_source` | Shentu 無法確認只有 root 能改它：成員不明的群組、讀不到的 ACL 或帳號資料庫、檢查和讀取之間被換掉的檔案，或沒辦法完整讀到網站伺服器的設定。 |
| `client_from_header` | 伺服器從標頭取用戶端位址（nginx 的 realip、Apache 的 mod_remoteip）。 |
| `custom_format` | 不是標準格式。它的紀錄行仍然會比對。 |
| `not_regular_file`、`symlink_not_followed` | 紀錄不是一般檔案，或要跟著連結才找得到。 |

未驗證的攻擊最多是中、不會到 L3、不算進 campaign，也不能從 Telegram 當封鎖依據。

**Debian、Ubuntu 的 nginx。** 照預設安裝時，nginx 和 PHP 都以 `www-data` 執行，logrotate 建立的存取紀錄是 `www-data:adm`（`create 0640 www-data adm`）。網站裡跑的程式碼改得了它，所以 v0.4.0 判為 `web_user_writable`：告警會送，但不能從 Telegram 當封鎖依據。手動改擁有者，下一次輪替又會被改回來。

**Rocky Linux。** nginx 的紀錄由它自己的 `nginx` 帳號建立，PHP-FPM（`apache`）寫不進去；v0.4.0 仍判為 `web_user_writable`，這只是判得比較保守。Rocky 預設的 httpd 設定會載入不在 Shentu 安全清單裡的模組，所以 Apache 的紀錄也一律判為 `web_user_writable`。這兩件事預計在 v0.4.1 處理。

## 實測

用合成請求量測，不是真實流量（`tools/detecteval`，在 CI 裡執行）：

- 從 nuclei-templates 轉出的請求：同類特徵比中 40.5%（3822 個中 1548 個）；比中不等於告警；
- 8 個應用程式、152 條路由的一般請求：363 個不同的請求誤報 0 筆，95% 上限約 0.8%；
- 針對測試主機真的有的漏洞的模板：10 個中 3 個告警，其中 2 個只到 L1（攻擊內容在請求本文，存取紀錄沒有記下）。

逐項的量測方式見[攻擊偵測的已知限制](attack-detection-limits.zh-TW.md#實測偵測率)。
